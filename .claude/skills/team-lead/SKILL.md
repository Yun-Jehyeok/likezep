# 팀장 진행 절차

팀 규칙은 `.claude/rules/team.md`. 이 절차는 메인 세션(팀장)이 따른다. 팀장은 조사·계획·분배·검증만 하고 구현은 역할 에이전트에게 맡긴다.

## 1. 접수

1. 간단한 질문이면 팀을 부르지 않고 바로 답한다.
2. 작업이면 GitHub 이슈를 만든다. 제목은 `[기능] …` / `[버그] …` / `[하네스] …`. 본문은 배경, 범위(하는 것 / 안 하는 것), 완료 조건(요구사항 ID), 승인 항목 여부. 보안·운영 세부는 `work/tasks/<이슈번호>-<이름>/`에 쓰고 본문에는 "로컬 기록 참조"만.
3. PM에게 한 줄로 알린다: 이슈 링크와 진행 순서.

## 2. 역할 순서

| 작업 | 순서 |
|---|---|
| 기능 | planner → qa(인수 테스트) → developer → qa(판정) |
| 버그 | (문서로 판단 안 되면 planner) → qa(재현 테스트) → developer → qa(판정) |
| 문서만 | planner |
| 하네스(훅·CI·센서·에이전트 정의) | 팀장 계획 → developer → qa(차단·오탐 시험) |

- 서로 기다릴 필요 없는 일만 동시에 맡긴다. developer는 한 번에 하나만 돌린다(worktree 보류, `docs/decisions.md` 2026-11-23). 같은 파일을 건드리는 일은 동시에 주지 않는다.
- developer 프롬프트에는 "인수 테스트 통과가 완료 기준, 인수 테스트 수정 금지"를 넣는다.
- qa에게 커밋을 시킬 때는 트레일러를 마지막 문단에 빈 줄 없이 한 덩어리로 쓰라고 적는다.
- qa 판정에 실행 근거가 없으면 돌려보낸다.

## 3. 에이전트에게 맡기기

- 프로젝트 에이전트 `planner`, `developer`, `qa`를 쓴다. 플러그인 `vocals-team:*`는 다른 프로젝트용이라 쓰지 않는다.
- 프롬프트에는 이슈 번호, 이번에 할 일, 이어 할 브랜치, 이전 단계 결과물만 넣는다. 대화 전체를 넘기지 않는다.
- 이슈별로 에이전트 ID를 기억해 둔다. 같은 이슈에서 그 역할이 다시 필요하거나 `[질문]`에 답이 나오면 새로 띄우지 않고 SendMessage로 그 에이전트를 이어 간다.
- 에이전트는 commit까지만 한다. push와 PR(draft로 열고, qa 판정 통과 뒤 ready)은 팀장이 한다.

## 4. 질문 전달

1. 받는 역할이 planner·developer·qa면 질문 블록만 그 에이전트에게 전하고, 답을 질문한 에이전트에게 돌려준다.
2. 오갈 때마다 이슈 회의록 댓글에 한 줄씩 남긴다(6장).
3. 같은 질문이 두 번 오가도 정리되지 않으면 PM 질문 목록에 넣는다.
4. 막힘이 "아니오"인 질문은 일을 멈추지 않는다.

## 5. PM에게 묻기

- 먼저 `docs/decisions.md`를 본다. 이미 정해진 것은 묻지 않고 따른다(출처를 회의록에 적는다).
- 되돌릴 수 있고 승인 항목·돈·법·약관·개인정보 공개 범위·범위 변경·운영 영향이 아니면 팀장이 정하고, 결정 로그에 남긴 뒤 다음 보고에 "팀장 결정"으로 알린다.
- 나머지는 모아서 한 번에, `.claude/rules/team.md`의 질문 형식에 번호를 붙여 묻는다. 답하지 않은 번호는 추천대로 확정한다. 승인 항목은 "PM이 명시적으로 '예'라고 해야 진행"이라고 따로 적는다.

## 6. 회의록과 마무리

- 회의록 댓글 형식:
  ```
  회의록 — qa 단계
  - developer→qa: (질문 요지) → (답 요지)
  - planner→PM: (질문 요지) → PM 답 대기
  ```
- PR 본문: `Closes #N`, 바뀐 파일 요약, 검증 결과(명령·통과 수), 트레이드오프(나빠진 지표·새 비용·보류한 대안), 바뀐 로컬 문서(`docs/`는 PR에 안 들어간다).
- 에이전트 보고의 `메모리` 줄은 팀장이 모아 둔다(에이전트 메모리는 하네스 4단계에서 연다).
- 하네스 파일(`.claude/`, CI, 센서)을 바꾼 PR에는 `harness` 라벨을 붙인다. 붙일 때 PR head 커밋을 회의록에 적고, merge 요청 직전 `git diff <그 커밋>..origin/<브랜치> --name-only`로 그 뒤 바뀐 하네스 파일을 다시 본다.
- qa가 실행 근거로 모두 통과라고 판정하면 PM에게 보고한다: PR 링크, 통과 수/전체 수, 남은 결정. merge는 PM이 한다.
- 하네스 단계 보고 형식:
  ```
  [보고] 단계: N | 상태: 완료 / 일부 완료 / 막힘
  - 바뀐 파일
  - 검증 결과: 훅 차단 시도 결과표, 검사 명령 결과, CI 결과
  - 남은 질문
  ```
