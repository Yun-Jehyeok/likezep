# ZEP 대체 온라인 멘토링 플랫폼 — 프로젝트 요구사항 정리

## 1. 프로젝트 배경 및 목적

- ZEP 플랫폼으로 온라인 멘토링을 운영 중이나, 여러 멘토링 그룹을 동시에 모니터링하기 위해 ZEP 스페이스를 2~3개 동시에 켜면 심각한 렉이 발생함
- ZEP은 10명을 초과하면 1인당 월 11,000원의 추가 비용이 발생하며, 목표 규모(30~50명)에서는 이 비용 부담이 상당함
- 위 두 가지 문제(성능, 비용)를 근본적으로 해결하기 위해 ZEP과 유사한 자체 온라인 멘토링 플랫폼을 직접 개발하기로 결정
- Discord와 같은 단순 화상회의 툴이 아니라, ZEP처럼 공간감/아바타가 있는 커뮤니티 느낌을 유지하는 것이 핵심 요구사항

## 2. 핵심 요구사항

| 항목 | 내용 |
|---|---|
| 목표 동시 접속 규모 | 30~50명 (향후 확장 가능성 있음) |
| 화상 형태 | 근접 기반 화상 채팅 (기본) + 전체 공지/발표용 화면공유 (가끔 필요) |
| 협업 도구 | 화이트보드 등은 현재 불필요, 추후 고려 |
| 모더레이션 | 강퇴/음소거 등 기능 없음 (사용 안 함) |
| 디바이스 | PC 전용, 모바일 지원 불필요 |
| 사용자 연령 | 전원 성인 (미성년자 없음) |

## 3. 렉 문제의 근본 원인 및 해결 전략

기존 ZEP에서 렉이 발생한 근본 원인은 **"ZEP 창 2~3개 = 완전히 독립된 앱 인스턴스 2~3개"** 구조 때문임 (스페이스당 약 250~300MB 메모리 사용 × 동시에 켠 탭 개수만큼 부하가 곱해짐).

이를 해결하기 위해 아래 원칙으로 설계함:
- 하나의 클라이언트가 여러 방(그룹)의 상태를 인지하되, 실제 무거운 리소스(영상 스트림, 렌더링)는 지금 보고 있는 방에만 사용
- 방 전환 시 새로고침 없이 즉시 전환, 이전 방의 리소스(텍스처, WebRTC 연결)는 확실히 정리(destroy/close)
- 근접 기반 화상은 mesh 구조라 방 전체 인원이 아닌 "근처 인원 수"에만 부하가 비례 → 총 인원이 늘어도 개인이 느끼는 부하는 그대로

## 4. 확정된 기술 스택

| 영역 | 기술 | 비고 |
|---|---|---|
| Core UI 프레임워크 | **React (Vite 기반 SPA)** | 로그인/로비/관리 대시보드 등 앱 셸 담당. 로그인 뒤에 있는 내부 도구 성격이라 SSR/Next.js 불필요 (추후 공개 랜딩페이지가 필요해지면 별도 정적 페이지로 분리) |

| 맵 제작 | **Tiled** | 직접 맵 제작 |
| 서버 호스팅 | **AWS + Docker** | 본인이 직접 관리/배포 |

### 아키텍처 구조
```

 └─ RoomView 컴포넌트

      ├─ colyseus.js (서버와 상태 동기화)
      └─ WebRTC mesh 연결 관리 (근접 인원과 화상)
```

## 5. 공간(존)/권한 구조

### 존(Room) 타입
```
전역 공지 채널 (mediasoup, 전체 구독)
 ├─ 공용 공간: 광장 (전체 접근 가능)
 ├─ 공용 공간: 회의실 (전체 접근 가능)
 ├─ 프라이빗 룸 A (그룹 A 멘티 + 담당 멘토만)
 ├─ 프라이빗 룸 B (그룹 B 멘티 + 담당 멘토만)
 └─ 프라이빗 룸 C (그룹 C 멘티 + 담당 멘토만)
```

### 역할별 권한
| 역할 | 룸 접근 권한 | 관리 권한 |
|---|---|---|
| **Admin** (본인) | 전체 룸 접근 | O — 그룹 생성/삭제, 유저 배정, 계정 관리 등 전체 |
| **외부 멘토** (추후 추가 가능) | 전체 룸 접근 (Admin과 동일) | X — 관리 대시보드 접근 불가 |
| **멘티** | 본인 소속 룸 + 공용 공간만 | X |

- 멘티는 타 그룹 프라이빗 룸 접근 불가, 회의실/광장 등 공용 공간은 접근 가능
- 계정: Google 소셜 로그인
- 그룹 배정: 관리자(본인)가 수동으로 진행 (멘티 최초 로그인 → 미배정 대기 상태 → 관리자가 그룹 배정)

## 13. PoC 상세 설계

> 실제 코드 개발은 설계 완료 후 claude-cli와 함께 로컬 환경에서 진행 예정. 아래는 개발 착수 시 바로 구현 가능한 수준의 설계 명세.

### PoC 1 — 근접 감지 + WebRTC Mesh 연결/해제 검증

**목표**: 아바타가 가까워지면 화상이 자동으로 붙고, 멀어지거나 방을 나가면 리소스 누수 없이 깔끔하게 끊기는지 검증. 렉 문제 해결의 핵심 가설(리소스 정리) 검증 단계.

**검증 항목 (Definition of Done)**
1. Colyseus 방에 2명 이상 입장 시 아바타 위치가 실시간 동기화되는가
2. 아바타 간 거리가 임계값 이내로 가까워지면 자동으로 WebRTC 연결이 맺어지고 화상이 뜨는가
3. 거리가 멀어지면 해당 연결이 정리(close)되는가 — 메모리/리소스 누수 없이
4. 방을 나가면 그 방의 모든 연결이 즉시 정리되는가
5. 3개 이상 근접 연결이 동시에 유지될 때도 각 스트림이 꼬이지 않는가

**최소 구현 범위**
- Tiled 없이 단순 그리드 배경, placeholder 아바타(사각형/원)
- 로그인 없이 이름 입력 후 바로 입장
- 방 1개만 (멀티룸 전환은 범위 밖)

**Colyseus 상태 스키마**
```ts
class Player extends Schema {
  @type("string") id: string;
  @type("string") name: string;
  @type("number") x: number;
  @type("number") y: number;
}

class RoomState extends Schema {
  @type({ map: Player }) players = new MapSchema<Player>();
}
```

**근접 감지 로직 (서버 측)**
- 100ms 간격 tick 루프에서 모든 플레이어 쌍의 거리 계산 (PoC 규모에서는 O(n²) 완전탐색으로 충분, 규모 확대 시 공간 분할 최적화 고려)
- 거리 < 임계값(예: 150px) → 미연결 쌍이면 시그널링 메시지 전송
- 거리 ≥ 임계값 → 연결 종료 메시지 전송

**시그널링 메시지 프로토콜 (Colyseus 메시지 채널 활용)**

| 메시지 타입 | 방향 | 내용 |
|---|---|---|
| `proximity-connect` | 서버→클라 | 상대방 id + offer 주체 지정 (항상 id가 작은 쪽이 offer) |
| `webrtc-offer` / `webrtc-answer` / `webrtc-ice` | 클라→서버→상대 클라 | WebRTC 시그널링 데이터 중계 (서버는 릴레이만) |
| `proximity-disconnect` | 서버→클라 | 상대방 id, 해당 PeerConnection close 지시 |

**클라이언트 연결 관리**
- `Map<peerId, RTCPeerConnection>` 형태로 활성 연결 관리
- 연결 해제 시 `pc.close()` + Map 제거 + video element 제거를 하나의 정리 함수로 통일 (메모리 누수 방지 핵심 지점)

**검증 시나리오**
1. 2명 입장, 멀리 있을 때 화상 없음 확인
2. 가까워짐 → 화상 자동 연결
3. 멀어짐 → 화상 끊김 + 리소스 정리 (개발자도구 메모리 프로파일링 확인)
4. 3명 동시 근접 → 3-way mesh 정상 동작
5. 탭 강제 종료(비정상 종료) → 다른 클라이언트들의 연결 정리 확인

### PoC 2 — coturn 기반 네트워크 환경 검증

**목표**: 다양한 실제 네트워크 환경(가정용 와이파이, 모바일 핫스팟, 학원망 등)에서 P2P 연결이 실패할 때 TURN 릴레이가 실제로 동작하는지 검증.

**검증 항목**
1. coturn 서버를 AWS EC2에 설치·구동
2. 같은 네트워크의 두 클라이언트 간 연결 (STUN만으로 가능한 기준선)
3. 서로 다른 네트워크 간 연결 — TURN 릴레이 동작 확인이 핵심
4. `iceConnectionState` 로깅으로 실제 사용된 ICE 후보 타입(`host`/`srflx`/`relay`) 확인
5. 연결 수립까지 걸리는 시간 측정 (실사용 체감 지연 판단 근거)

**최소 구현 범위**
- coturn 설정: `listening-port`, `realm`, 인증 설정
- 클라이언트 `RTCPeerConnection`의 `iceServers`에 STUN + 자체 TURN 등록 (PoC 1 코드 재사용, iceServers 설정만 추가)

**보안/설정 체크포인트**
- TURN 인증은 정적 credential 대신 **시간 제한 임시 credential(REST API 방식)** 권장 — credential이 클라이언트에 노출되는 구조라 고정 값은 악용 소지 있음
- AWS 보안그룹에서 coturn UDP 포트(기본 3478 + relay용 포트 범위) 개방 필수 — "로컬에선 되는데 AWS에선 안 되는" 흔한 실패 지점

**검증 시나리오**
1. 두 클라이언트 모두 유선망 — 연결 확인
2. 모바일 핫스팟 vs 집 와이파이 — TURN 릴레이 경유 확인
3. TURN 서버를 끈 상태에서 2번 재현 → 연결 실패 확인 (TURN 필요성의 대조군)

### PoC 3 — 경량 mediasoup 화면공유 포워딩 검증

**목표**: 발표자 1명의 화면공유 스트림을 서버가 받아 나머지 전원(수십 명)에게 안정적으로 전달할 수 있는지 검증. mediasoup을 "1 producer → N consumers" 최소 케이스로만 구현.

**검증 항목**
1. mediasoup 서버(Worker/Router) 기동 및 transport 연결 수립
2. 발표자가 `getDisplayMedia()`로 화면공유 스트림을 produce
3. 나머지 클라이언트들이 consume — 10명 이상 동시 시청 시 화질/지연 실사용 가능 여부
4. 발표 중단 시 모든 시청자 쪽 리소스 정리
5. 발표 중간 입장 유저도 진행 중인 화면공유를 바로 수신 가능한지
6. 서버 CPU/대역폭 측정 → 30~50명 규모 EC2 스펙 산정 근거 확보

**최소 구현 범위**
- 비디오 producer 1개 + consumers N개만 (오디오 믹싱, 다중 producer, simulcast 제외)
- 시그널링은 PoC 1의 Colyseus 메시지 채널 재사용 (`screenshare-start` / `screenshare-transport` / `screenshare-stop` 메시지 추가)
- 발표 권한은 하드코딩 플래그로 처리 (정식 권한 체계는 MVP 단계에서 연결)

**아키텍처 (전역 공지 채널)**
```
발표자 (Admin/멘토)
   │ produce (화면공유 스트림, WebRTC transport)
   ▼
mediasoup 서버 (EC2, Docker)
   │ consume × N
   ▼
전체 시청자 (룸 위치와 무관하게 구독 — "전역 공지 채널")
```
- 룸(존) 경계와 무관한 전역 채널이므로 Colyseus 룸 상태와 분리된 별도 연결로 관리

**삽질 방지 체크포인트**
- mediasoup의 RTC UDP 포트 범위(min/max port) 보안그룹 개방 필요
- EC2에서는 `announcedIp`에 퍼블릭 IP 명시 필수 (사설 IP 바인딩 문제로 배포 후 연결 실패하는 흔한 지점)
- `getDisplayMedia()` 호출 시 최대 해상도/프레임레이트 제약(예: 1080p, 15fps)으로 대역폭 관리

**검증 시나리오**
1. 발표자 1명 + 시청자 2~3명 기본 동작
2. 시청자 10명+ 부하 테스트
3. 발표 중 시청자 비정상 종료 → 서버 리소스 정리 확인
4. 발표자 비정상 종료 → 전체 시청자 화면 정리 확인

## 14. MVP 화면 명세

### 화면 목록
```
[공통]
 1. 로그인 화면 (Google OAuth)
 2. 배정 대기 화면 (그룹 미배정 멘티용)

[멘티/멘토 공통]
 3. 로비 화면 (입장 가능한 룸 목록)
 4. 룸 화면 (맵 + 아바타 + 근접 화상 + 채팅) ← 핵심 화면
 5. 화면공유 시청 뷰 (룸 화면 위 오버레이)

[멘토/Admin 전용]
 6. 방 스위처 (룸 화면 내 오버레이)

[Admin 전용]
 7. 관리 대시보드 (/admin)
```

### 화면 1 — 로그인
- Google OAuth 버튼 하나만 있는 심플 페이지
- 로그인 성공 → 배정 상태 확인 → 배정됨: 로비 / 미배정: 대기 화면

### 화면 2 — 배정 대기
- "관리자가 그룹을 배정하면 입장할 수 있어요" 안내 문구
- 주기적 폴링 또는 새로고침 버튼으로 배정 여부 확인 (실시간 푸시 불필요)

### 화면 3 — 로비
- 입장 가능한 룸 카드 목록: 멘티는 [본인 그룹 룸 + 공용 공간], 멘토/Admin은 전체
- 카드에 현재 접속 인원 수 표시, 클릭 시 룸 입장

### 화면 4 — 룸 화면 (핵심)

**레이아웃**
```
┌─────────────────────────────────────────────┐
│ 상단 바: 룸 이름 | 현재 인원 | [방 스위처*]      │
├────────────────────────────────┬────────────┤
│                                │            │
│    PixiJS 캔버스 (맵 + 아바타)    │  채팅 패널   │
│                                │ (접기 가능)  │
│  ┌────┐ ┌────┐                 │            │
│  │화상1│ │화상2│ ← 근접 화상       │            │
│  └────┘ └────┘                 │            │
├────────────────────────────────┴────────────┤
│ 하단 바: 마이크 | 카메라 | 화면공유** | 나가기     │
└─────────────────────────────────────────────┘
* 방 스위처: 멘토/Admin에게만 노출
** 화면공유 시작 버튼: 멘토/Admin에게만 노출
```

**인터랙션**
- 이동: 방향키/WASD (PC 전용, 클릭 이동은 MVP 제외)
- 근접 화상: 자동 연결/해제 (PoC 1 로직), 우상단 부유 타일 최대 4~5개
- 마이크/카메라: 트랙 단위 mute/unmute 토글 (연결 유지)
- 채팅: 룸 단위 전체 채팅
  - Colyseus `chat` 메시지 브로드캐스트
  - **채팅 기록 DB 저장** (룸별 메시지 테이블 — 재입장 시 최근 기록 로드, 로그/리뷰 용도로도 활용 가능)
  - 채팅 입력 중 WASD 이동 비활성화 (입력 포커스 충돌 방지)

### 화면 5 — 화면공유 시청 뷰
- 공유 시작 시 화면 중앙 오버레이로 표시, 시청자가 최소화 가능

### 화면 6 — 방 스위처 (멘토/Admin 전용)
- 상단 바 버튼 → 드롭다운/패널로 전체 룸 목록 + 룸별 인원수
- 클릭 시 현재 룸 리소스 정리(텍스처 destroy, WebRTC close) → 페이지 리로드 없이 즉시 새 룸 입장

### 화면 7 — 관리 대시보드 (Admin 전용, `/admin`)
- **7-1 실시간 현황**: 전체 룸 그리드, 룸별 접속자 이름 목록 (수 초 간격 폴링)
- **7-2 그룹 관리**: 그룹 생성 폼 + 유저 테이블 (이름/이메일/역할/소속 그룹 드롭다운)
- **7-3 로그/통계**: 입장/퇴장 이벤트 테이블 + 그룹별 이용시간 합계 (차트는 추후)
